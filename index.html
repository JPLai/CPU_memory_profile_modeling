Report

Four cores get you about 90% of the speedup

We timed a CPU-heavy job 1,552 times on a 12-core laptop, varying the number of cores (1–12) and the job size (1–100 units). Repeated runs agree closely, and two simple formulas predict both run time and memory.

Why build a model at all

Collecting data is no longer the hard part. The 1,552 runs behind this report took 49 minutes. The code that ran them, with randomized order, crash-safe logging, resume and integrity checks, was built with AI coding help in about a day, along with the analysis. A few years ago that tooling alone was weeks of work, so studies stayed small and models were built on thin data.

But a table of 1,552 timings still doesn't answer the questions we care about. A model does.

What a model gives you

  • An explanation. Time is rounds × cost per round. Memory is idle workers plus busy workers.
  • Predictions for runs we never made, instantly. That is what a scheduler or optimizer needs.
  • A check on the data. The k = 8 runs stood out because they didn't fit. Their timestamps showed they ran during a load spike.
  • Compression. Seven numbers replace 1,552 rows.

What changed, and what didn't

  • No longer a blocker: writing the instrumentation, running hundreds of randomized runs, cleaning and checking the data, fitting and plotting.
  • Still the real work: deciding what to measure, designing the experiment, and judging whether a result is real.
  • This study shows both. Data collection was clean: every row passed its integrity checks. The one real flaw was a design choice, running each core count in one stretch, and only careful checking caught it.

So the work moves from building tools to asking better questions. That makes modeling more useful, not less: we can afford to test more ideas, check them properly, and rerun when something looks wrong.

Where adding cores stops paying off

For a 100-unit job, going from 1 to 4 cores cuts run time from 16.6 s to 3.3 s. Adding 8 more cores saves only another 1.7 s, about 0.2 s per extra core. When the machine is busy with other work, extra cores past 4 save nothing at all.

What we measured

One unit of work draws 20 million random numbers (a 160 MB array) and averages them. A job is n units, spread over a pool of k worker processes. For every combination we recorded how long the job took on a wall clock and the peak memory of all the processes together.

The measurements repeat closely

When conditions are steady, running the same scenario again gives almost the same answer. For 9 of the 12 core counts, repeated time measurements differ by 7% or less, typically 2–3%. Memory repeats within 6% at every core count.

Typical spread between repeated runs (median coefficient of variation), steady-load half of the session. Orange bars mark the three core counts with a few slow outliers.

The three noisy core counts are explained by when they ran, not by the measurement. k = 1 ran first, right after the run was restarted. k = 8 and k = 11 ran last in the second block, around 20:09, just as background load started rising. Their runs from the first block sit right on the trend line.

The response surfaces

Time falls steeply as cores are added and grows with job size in steps, because a job runs in rounds of k units. Memory climbs in a straight line with cores and flattens along job size once there are more units than cores.

Two simple models fit the data

Both models come from how the job runs, not from curve fitting. That is why they need only three or four numbers each.

Run time: rounds × cost per round

time = 0.02 + rounds × (0.183 − 0.0214·k + 0.00214·k²)

rounds = ceil(n / k). The bracket is the cost of one round, which grows slowly as cores compete for memory bandwidth. Example: 6 cores, 100 units → 17 rounds × 0.13 s ≈ 2.3 s.

Held-out error 0.27 sR² 0.991

Peak memory: idle + busy workers

memory = 128 + 72.7·k + 138.8·min(k, n) MB

Every worker costs about 73 MB just by existing, and each busy worker adds about 140 MB for its data. Example: 6 cores, 100 units → about 1,400 MB.

Held-out error 2.3%R² 0.997

Errors are measured on 37 scenarios held back from fitting. The simpler forms in the original plan (time from rounds and k, memory from k and n) had 26% and 17% error.

Limits

  • About halfway through the session, other programs started using the CPU and runs got about 2.4× slower. The time model uses the steady first half; memory was barely affected.
  • Short jobs (under a second) have larger relative errors, around 19%.
  • The results apply to this machine, 1–12 cores and 1–100 units of 20M numbers.
  • Next run: mix the core counts in time instead of running each one in a single stretch, and log CPU load for each run.

Scaling at n = 100

Steady load: 16.6 s → 3.3 s by k = 4 (89% of the total reduction); k = 4 → 12 adds 1.7 s, about 0.2 s per extra core. Heavy load (blocks 3–4): the minimum is reached by k ≈ 4–6 and higher k is no faster.

Caveats

  • Background CPU load (baseline 19–36%) rose between blocks 2 and 3, slowing runs about 2.4×, most at high k. The regime split was chosen after seeing the data.
  • All runs for one k ran together within a block, so load drift is confounded with k. This explains the k = 8 and k = 11 outliers (end of block 2, 20:08:58–20:10:32) and the slow k = 1 runs (first in block 1, right after restart).
  • Short-job relative error is about 19%; valid for k = 1–12, n = 1–100, 20M draws per unit, this CPU.
