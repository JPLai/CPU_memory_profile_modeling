Goal 1

A profile makes estimates deterministic

With the task–CPU–memory profile, the time and memory of any task are a lookup, not a measurement. You know the cost before you run it.

Goal 2

The profile makes 10,000 tasks easy

Choosing cores for one task is trivial. For 10,000 tasks of different sizes, the profile turns the decision into a small integer program that solves in milliseconds.

Goal 1

The task–CPU–memory profile

A profile is the cost of a task for every combination of size n (1–100 units) and cores k (1–12): its run time, its peak memory, and the core-time and memory-time it uses. All 1,200 cells come from two formulas fitted in step 1.

t(n,k) = a + ⌈n/k⌉ · (b + c k + d k²)
Run time: rounds of k units at a time, times the cost of one round.
m(n,k) = 128 + 72.7 k + 138.8 · min(k, n)  MB
Memory: a base, every idle worker, every busy worker's data.

The constants a–d have one set of values for a steady machine and one for a busy machine. Either way, the estimate is fixed by n and k, not drawn from new measurements. That is what "deterministic" means here.

How close the lookup is depends on the machine. On a steady machine, repeated runs agree within about 2–4%. On a busy machine, they vary by about 12%, so estimates are rougher.

One task

Estimating one task is simple

For one task, read the profile row for its size and pick the best of 12 core counts. A 100-unit task on a busy machine runs fastest at 8 cores (6.7 s), uses the least core-time at 1 core (23.7 core-seconds), and stops getting faster after about 5–6 cores. No solver needed.

Goal 2

What if 10,000 tasks arrive, all different sizes?

Now every task needs a core count, they all share 12 cores and a memory budget, and each choice costs core-time and memory-time while faster tasks earn a reward. Choosing per task looks like a huge problem. The profile shrinks it.

Decide task by task100,000binary variables: 10,000 tasks × 10 options (4–12 cores, or not run)
Decide by size, using the profile1,000integer variables: 100 sizes × 10 options. Tasks of the same size have the same profile, so they face the same choice.

The model in words

Decide
For each task, how many cores it gets, or whether it runs at all in this window.
Maximize
The award for every task finished, where a faster finish earns more,
minus the cost of the core-time it uses,
minus the cost of the memory-time it uses.
Subject to
  1. One choice per task. Every task picks exactly one option: a core count, or "not run".
  2. Max run time. A task can't take an option that would run longer than the time limit.
  3. Core bounds. A task gets between the minimum and maximum cores allowed, for example 4 to 12.
  4. Memory bound per task. A task can't take an option that needs more memory than one task is allowed.
  5. The machine's limits. All the core-time used fits in 12 cores over the time window, and all the memory-time fits in the memory budget.

Rules 2–4 don't need equations: they just remove options from the list before solving. Only rules 1 and 5 tie the tasks together.

Everything nonlinear (the rounds, the k², the min) lives inside t and m, which the profile computes ahead of time. What's left is linear. The per-task version, with a binary yjk for each task, gives the same answer with 100 times more variables.

The "not run" option is what makes "tasks finished" matter: when the window is too short for everything, the model picks which tasks are worth running. If every task must run, drop it; the award is then the same for every plan, and the model becomes "minimize cost". The capacity rules treat cores and memory as averages over the window. Packing whole tasks onto cores, and their order, is step 3.

Solved: 10,000 tasks

This example is the every-task-must-run case. There is no "not run" option, and instead of a fixed window, each second of makespan has a price γ.

α per core-second, β per GB-second, γ per second of makespan. Solved with HiGHS through SciPy. The LP relaxation was already integral, so the integer answer matched it exactly.

Cores chosen for each task size, at three values of the run-time reward ρ. One choice per size.

With no reward, almost every size gets the minimum of 4 cores, the most efficient option. As the reward grows, sizes move up to 5–9 cores, and core counts that divide a task's size evenly are favored (a 7-unit task on 7 cores runs in one round).

Each point is one solve. Raising the reward buys shorter tasks with a longer total run.
Reward ρAvg coresAvg run timeMakespanCore-hours

The trade-off is steep. Cutting average task run time by 19% (4.0 s to 3.3 s) stretches the makespan by 55% (3.7 h to 5.8 h), because extra cores per task are used less efficiently. Past ρ ≈ 50, tasks barely get faster while the batch keeps getting longer.

Memory matters once it is tight. Lowering the budget from 8 GB to 2.4 GB leaves the core choices nearly unchanged but stretches the makespan from 3.7 h to 4.5 h, because fewer tasks fit in memory at once.

From the profile to capacity planning

If you collect the task profile by hour, meaning how many tasks of each size arrive each hour, this same model tells you how many machines you need and how fast you can process the work. Set the time window to one hour, feed in that hour's task counts, and read off the core-time and memory-time the best plan needs.

Machines needed≥ 410,000 tasks an hour like these need about 45 core-hours per hour at 4 cores per task: 3.7 machines of 12 cores running flat out.
Throughput per machine~2,700tasks an hour per 12-core machine, at the most efficient core choice.

These are lower bounds: they assume every core is busy all the time. Real queues need headroom.

What the model can't tell you is the order tasks run in and how long each one waits. Scheduling and wait-time estimates still need to go back to simulation, using the profile as the simulation's input.

Limits and next step

  • The profile was measured with one task on the machine at a time. With 10,000 tasks the machine is always full, and tasks running together may slow each other. A short concurrency test should come before trusting these numbers.
  • The busy-machine profile is used here because the steady-load profile has an inflated 1-core value from the first minutes of the run. Its estimates are rougher (about 12% run-to-run spread).
  • Run time here means time spent running. If waiting time matters, the order of tasks matters too.
  • Step 3: turn the size → cores table into a real schedule, simulate it, and measure the gap from this MIP.
